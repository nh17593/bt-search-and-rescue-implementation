Human Victim Rescue: Scout, Medic, Guard

Importable trees and exact manual node settings for the native human-victim Operation Quick Rescue scene. Reviewed upstream commit: d9db22b22fe4b4f3c2c13436ccee6dd010bb60e8.

SetupScoutMedicGuardVerification
Native rescue semantics: Rescue Victim marks a human rescued in place and increments the robot's human-rescue count. Medic then returns to SZ by itself. These trees do not simulate carrying or delivering human bodies. The package-delivery count stays zero.

Setup and repeat trials

Read README.txt for the full setup, source references, limits and verification procedure.

  1. Open a fresh playground page. Select Operation Quick Rescue to initialize native humans and V2's schedule.
  2. Import bt_tree.json and bt_sim_config.json together, then Apply.
  3. Confirm R1 → R1 Scout, R2 → R2 Medic, R3 → R3 Guard. Select the imported R1 Scout tab before Reset. This restores Scout's three ID filters from its library entry.
  4. Set Robot speed=10, FOV=360°, sensor ranges R1=200/R2=80/R3=42, communication ranges=300, battery drain=0.7. Press Reset once before the first step.
  5. Run with Scout's tree displayed. Use Explain or the BB selector to inspect other robots. Changing BT tabs during a run remaps IDs used by task memory.
  6. Every new trial: reload the page, reload Operation Quick Rescue, reimport both files, select Scout, set speed and Reset. Reset alone does not restore human rescued flags or V2's consumed schedule.

The JSON importer's environment handling omits human victims. The supplied victim array documents the intended scene, but loading the native human scene first is required. There are zero packages. The native Safe Zone rectangle is retained.

Manual build conventions

Create one BT per robot. Tables list preorder numbers, parents and children. Preserve the exact left-to-right sibling order; the engine sorts siblings by horizontal canvas position. Decorators and Root have one child. P3 on Victim Near? is the ID filter; do not omit it.

Put a coordinate pair entirely in Navigate To's Target/P1, leaving P2 empty. Human Approach nodes use the local BB key target_V0, target_V1 or target_V2. The current engine resolves those keys to Scout's received coordinates. Use each table's exact Config Params.

All mission BB state is local. Topic names retain their leading slash. Publish Topic uses bb:report and sends a JSON string; Medic Read Topic writes the string to victim_report. Do not replace it with a native object without adapting the receiver. Current topics are global and ignore communication range.

Custom Process code appears below each tree and in matching .js files. Paste it in the node's Expression field. It runs inside the node; do not execute those snippets in DevTools.

R1 Scout

Every tick, read corridor topics, independently sense V0/V1/V2 using native ID-filtered human sensors, remember visible coordinates, publish a cumulative report, and resume the exploration itinerary. The report never directly queries ENV.victims. Each sensor failure is optional, so hidden V2 cannot block other reports.

    const report = JSON.parse(bb.victim_report);
    for (const [id, v] of Object.entries(report.found || {})) {
      if (['V0','V1','V2'].includes(id) && Number.isFinite(v.x) && Number.isFinite(v.y)) {
        bb.known[id] = v;
      }
    }
  } catch (e) {}
}
const v2 = bb.known.V2;
const deadline = v2 && Number.isFinite(v2.expires) ? v2.expires : 35;
bb.urgent = !!(v2 && !bb.done.V2 && !bb.v2_timedout && tick < deadline);
bb.ordinary_allowed = !!(bb.done.V2 || bb.v2_timedout || tick >= deadline);
for (const id of ['V0','V1','V2']) {
  bb['pending_'+id] = !!(bb.known[id] && !bb.done[id]);
  if (bb.known[id]) bb['target_'+id] = bb.known[id].x+','+bb.known[id].y;
}
bb.all_rescued = !!(bb.done.V0 && bb.done.V1 && bb.done.V2);
bb.mission_finished = !!(bb.done.V0 && bb.done.V1 && (bb.done.V2 || bb.v2_timedout || tick >= deadline));
